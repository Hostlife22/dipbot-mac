# Ошибки возврата FLOSS, создание Trader и method vectors

2026-09-24. Статический анализ и эмуляция на Mac. Оригинальное приложение, Windows DLL и реальные RPC/транзакции не запускались. Весь запрошенный список остаётся незакрытым; ниже конкретные результаты этого прохода.

## Проверка влияния исправления Envi

Выполнены два полных ограниченных FLOSS-прохода по тем же восьми помощникам и одному неизменённому expanded.viv: baseline и исправление точной инструкции `48 c7 c0 ff ff ff ff`. В обоих случаях восстановление начального snapshot перед каждым caller включено. Исправление действует только внутри Python-процесса сравнения; установленные пакеты и EXE не менялись.

| Измерение | Baseline | Исправление Envi |
|---|---:|---:|
| Извлечённые контексты | 426 | 426 |
| Ошибки восстановления PC | 8 | 8 |
| Stack / tight / decoded strings | 0 / 0 / 0 | 0 / 0 / 0 |
| Применения исправления MOV | — | 0 |

Совпадают счётчики контекстов каждого helper и все восемь сообщений об ошибках. **В этом корпусе исправление MOV не устраняет прежние ошибки возврата: соответствующая инструкция не исполнялась.** Это закрывает проверку влияния на данный повторяемый проход, но не утверждает, что исправление бесполезно в других функциях.

Доказательства трёх завершённых проходов: [FLOSS_ISA_COMPARISON.json](FLOSS_ISA_COMPARISON.json). Третий проход наблюдал параметры проблемных вызовов, не меняя их поведение.

## Что происходит на восьми ошибках

Все ошибки происходят в трёх местах: `0x142905efc` (3), `0x14290635d` (3), `0x142906cc1` (2). Вызов направлен в thunk `0x14292c754`, который переходит в импорт `memcpy`.

Для всех восьми наблюдений:

- источник равен `0xfefefefefefeff16`, то есть типичный заполнитель плюс смещение 0x18;
- размер равен 17868022691004938224, результату сдвига заполнителя на 3 в 64-битном представлении;
- источник и назначение не отображены в память; указатель стека к моменту вызова тоже имеет неподготовленное значение;
- после обработки вызова PC/слот возврата содержат заполнитель `0xfefefefefefefefe`.

Native-код берёт источник из поля `+0x98`, добавляет 0x18 и умножает значение поля `+0xa0` на 8. Наблюдения указывают на неподготовленные данные функции/массива аргументов и последующее некорректное вычисление стека. Они **не** подтверждают ошибку настоящего memcpy или повреждение памяти работающего Windows-бота. Размеры и адреса из эмулятора не следует трактовать как реальный запрос копирования. Поле overlap в трассе — простая числовая проверка без моделирования переполнения указателя, не доказательство безопасности копирования.

Следующий технический барьер — восстановление полей объектов и соответствующих массивов до вызова helper. Подмена размера нулём или принудительное восстановление PC скрыла бы проблему, поэтому не применялась.

## Создание исходного класса Trader

[TRADER_NAMESPACE_EVIDENCE.json](TRADER_NAMESPACE_EVIDENCE.json) описывает участок инициализации `0x141e84d3e–0x141e86cb1`:

1. Создаётся новый словарь namespace (R14).
2. Найдены **50 явных записей**: `__module__`, `__qualname__` и 48 методов. Неразрешённых вызовов исследованного setter в этом диапазоне нет.
3. Конструктор использует импорт `PyType_Type`, имя Trader, общий пустой tuple баз и namespace. Тип контейнера подтверждён непосредственно тегом `T` и нулевым размером в ресурсе, а не только представлением `[]` декодера.
4. Результат записывается в модуль под именем Trader.

В этом namespace нет `close`, `__del__`, `__getattr__`, `__getattribute__`. Для обычного свежесозданного класса отдельный close-метод здесь не определяется; `_close_trader` — проверка опционального атрибута. Поэтому отсутствие найденного `Trader.close` нельзя автоматически считать пропущенным native-телом метода.

Граница доказательства: перечислены явные записи штатного построения класса, не доказано отсутствие произвольных последующих изменений атрибутов, альтернативных binding Trader и косвенных мутаций. Полное завершение внешних задач этим не восстановлено.

## Аргументы двух- и трёхаргументных методов

Разобраны помощники `0x142911b40` и `0x142911ca0`: receiver в RDX, имя в R8, адрес вектора в R9. После разрешения атрибута/дескриптора они передают вектор соответственно в известные call_vector2/call_vector3. Анализатор теперь сохраняет выражение результата и порядок аргументов, оставляя неизвестные значения неизвестными.

[METHOD_VECTOR_FLOW.json](METHOD_VECTOR_FLOW.json) содержит повторный проход 231 тела функций. Примеры:

- `_convert_base → _make_trader`: второй аргумент прослежен до входного `arg[2]`, первый неизвестен;
- `_convert_base → execute_quote_to_bnb`: второй аргумент связан с результатом `preview_quote_to_bnb()` созданного Trader; первый пока неизвестен;
- `run → _sell_target`: второй аргумент связан с результатом глобального `choose_registered_candidate()`;
- `run → _convert_base`: три значения пока остаются неизвестными.

Это уточнение происхождения значений, а не доказательство реального типа объекта или полного поведения маршрута. Регрессионный тест проверяет, что вектор читается из R9 и не смешивается с именем метода в R8.

## Воспроизводимость и проверки

В окружении FLOSS:

```bash
python -m tools.floss_isa_comparison /path/to/reference.exe --workspace /path/to/expanded.viv --output-dir /tmp/isa-baseline
python -m tools.floss_isa_comparison /path/to/reference.exe --workspace /path/to/expanded.viv --output-dir /tmp/isa-fixed --corrected
python -m tools.floss_isa_comparison /path/to/reference.exe --workspace /path/to/expanded.viv --output-dir /tmp/isa-memcpy --trace-memcpy
```

В окружении Capstone/pefile:

```bash
python -m tools.trader_namespace /path/to/reference.exe --output docs/TRADER_NAMESPACE_EVIDENCE.json
python -m tools.unwind_inventory /path/to/reference.exe --lookups docs/GLOBAL_LOOKUP_EVIDENCE.json --output docs/METHOD_VECTOR_FLOW.json
python -m unittest discover -s tools/tests -q
```

**30 тестов инструментов прошли**, Python compile и diff check без ошибок. Production не менялся; последний полный pytest приложения — 336 passed, повторно не запускался. Коммит/push не выполнялись.
