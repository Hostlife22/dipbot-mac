## 1. Цель и границы

Сократить время от локального получения актуального рыночного события до отправки
и ответа RPC на **торговый swap**, сохранив стратегию, корректность сумм и восстановление.
Измерять отдельно обнаружение события, BUY, SELL, approve, конвертацию и Sweep.
Быстрый approve не считать быстрым исполнением покупки.

Рынок пользователя — первые минуты после миграции мем-токенов. Один длинный прогон
на затухающем токене не характеризует ни скорость, ни качество стратегии. Для
проверки использовать несколько свежих рынков и сохранять контекст ликвидности.
Фильтры угасания, возраст миграции и изменение правил повторного входа — отдельная
стратегическая задача: не включать их незаметно в performance-оптимизацию.

На первом этапе доступны public RPC, офлайн-тесты, read-only, PAPER и локальный fork.
Paid RPC измеряется после предоставления endpoint; отсутствие доступа отмечается
как непроверенное, а не заменяется обещанием скорости. План не разрешает новые LIVE-траты.
Предыдущий лимит $1 не обнуляется: в статусе уже зарезервировано около $0,942.
Ключи, подписанные raw-транзакции и URL с credential не включать в отчёты/коммиты.

## 2. Поправки к исходному предложению

| Исходная идея | Исправленное требование |
| --- | --- |
| Вынести все записи из hot path | Диагностику можно вынести; **durable intent/hash до broadcast обязателен**. Нельзя убирать fsync ради красивого latency |
| RPC принял → mempool → block → confirmed | Это разные наблюдения. Ответ с hash не доказывает распространение по сети; receipt не равен финальности |
| T0 начинается с price event | Разделить доставку head/log, начало HTTP-чтения, получение ответа и готовность согласованной цены; иначе задержка polling останется невидимой |
| Кешировать nonce, allowance, gas | Метаданные и изменяемое состояние имеют разные правила. Локальный nonce/estimateGas без проверки не являются безопасной заменой текущих защит |
| WebSocket вместо polling | Сначала сравнить shadow-потоки; WSS может терять события и менять частоту наблюдений стратегии |
| Локальная цена из событий | V2 reserves и V3 spot — не исполнимая котировка на размер сделки. Не заменять ими minOut, quote или проверку продажи |
| Убрать ожидание receipt | Receipt approve может быть зависимостью swap; receipt swap нужен для учёта фактической позиции. Ускорять наблюдение, не разрешать конкурирующие сделки |
| Всё независимое запускать параллельно | Только ограниченные read-only задачи с согласованным снимком; единственный владелец nonce/позиции/журнала сохраняется |
| Оптимизировать entry | SL/выход и STOP имеют как минимум тот же приоритет; улучшение BUY не должно ухудшать SELL |
| Получить p99 из короткого прогона | Всегда показывать N, ошибки и неполные traces; пять сделок не дают устойчивую оценку p99 |
| Указать заранее X → Y миллисекунд | До baseline значения UNKNOWN. Целевые бюджеты фиксируются после измерений, до оптимизаций |

## 4. Карта исполнения и первичная матрица

Текущий основной путь:

```text
HTTP polling / WSS head hint → Worker scheduling → Chain.price → Strategy.observe
 → entry conditions/quote → durable operation intent → pool/router/balance/quote
 → allowance → [approve: prepare → sign → durable hash → send → receipt]
 → свежая quote/minOut → snapshots → nonce/gas/balance → build → sign
 → durable hash → sendRawTransaction → ACK → receipt/canonical check
 → фактические балансы → position/accounting save → finish
```

Направление оптимизации, НЕ утверждение о готовой новой архитектуре:

```text
проверенные метаданные + прогретые соединения + shadow WSS + bounded read workers
 → актуальный согласованный снимок → прежняя стратегия → необходимые проверки
 → единственный executor → build/sign → durable intent/hash → один broadcast
 → наблюдение receipt/каноничности → учёт → разрешение следующей операции
```

| Этап | Известные вызовы/ожидания | Параллельность, подготовка и кеш |
| --- | --- | --- |
| Планировщик | Очередь Worker, polling, HeadSchedule; замерить ожидание и возраст события | WSS будит чтение; не накапливать устаревшие задания |
| Цена V2/V3 | latest header; V2 reserves либо V3 Multicall; canonical read при новом снимке; chainId по политике | Только block/hash-consistent кеш. Считать wire calls, включая middleware |
| DIP/TP/SL | Локальная стратегия; quote-based exit добавляет сетевую quote | Decimal/int сохранить; замер отдельно от RPC и UI |
| Entry checks | Activity при включённом фильтре; round-trip quote, freshness, стоимость | Только доказанно независимые чтения; не выкидывать фильтры |
| Pool/router/allowance | Несколько eth_call/getCode/balance; количество зависит от ветви | Подготовить ABI/metadata; политика инвалидирования обязательна |
| Approve/convert | Отдельные транзакции, возможно несколько | Отдельный latency cohort; не выдавать прогрев за разрешение заранее тратить газ |
| `send` | pending nonce + latest nonce, estimateGas, balance, проверки сети и build | Сначала измерить; сейчас вызовы синхронные в executor, UI не блокируют |
| Signing + durable save | Локальные CPU/JSON/файловые операции | Signing после окончательных параметров; durability остаётся барьером |
| Broadcast | Один sendRawTransaction, отдельный endpoint опционально | Таймаут ответа не означает отказ приёма; не повторять автоматически |
| Receipt/учёт | Сейчас ожидание до 120 с, polling 0,2 с; balance/canonical/save | Не входит в ACK той же tx, но может блокировать последующий swap после approve |

**Latencies и точные RPC counts пока UNKNOWN.** Статическое количество верхнеуровневых
вызовов не равно количеству HTTP round trips. На этапе baseline дополнить каждую
строку p50/p95, числом wire requests, зависимостями и критическим путём отдельно
для BUY/SELL, V2/V3, cold/warm, approve-needed/ready, converter/direct.

## 5. Метрики и трассировка — P0.1

Расширить существующие CycleTrace/Timings; использовать `perf_counter_ns()` внутри
процесса. Trace содержит session/cycle/operation/transaction/attempt ID, side,
mode, pool, block number/hash, поколение выбора рынка, источник и outcome.
Endpoint обозначать безопасным alias. Не сохранять calldata/raw tx/ключи/полные URL.

События измерения:

- E0: локальный приём head/log; для HTTP — начало и конец чтения отдельно.
- T0: локальное получение исходных market data; T1: готова проверенная цена.
- T2: завершено решение стратегии; T3: завершены entry/exit conditions.
- T4: начало подготовки **конкретной** tx; T5: nonce готов; T6: gas готов.
- T7: tx построена; T8: подпись готова; J0/J1: начало/конец durable save.
- T9: вызов sendRawTransaction; T10: ответ RPC и проверка локального hash.
- T11: первое локальное наблюдение receipt включения, отдельно canonical validation.
- T12: наблюдение финальности по явно определённому правилу, если поддержано.

Сохранить исходный T0 через очереди: извлечение из очереди не должно обнулять возраст.
T5/T6 могут идти параллельно; это spans/DAG, а не обязательная цепочка разностей.
Отсутствующие стадии — null с причиной, не ноль. Для PAPER signing/ACK/inclusion — N/A.
Для нескольких tx хранить первый и последний ACK, отдельно ACK целевого swap.

Основные метрики: E0→T1, T0→T2, T2→T3, T4→T8, J0→J1, T8→T9,
T9→T10, **T0→T9 и T0→T10 swap**, T0→T11, T0→T12, signal age при отправке.
Также: RPC count, очередь, retries, stale/rejected signals, STOP latency, fsync,
CPU/RSS/threads, drops диагностики и записей рынка, revert/unknown outcome rate.

Среднее, median/p95/p99/max, N и диапазон времени показывать по одному cohort.
Не складывать p95 отдельных этапов как p95 всего цикла. Не смешивать успешные
и неуспешные попытки без маркировки; ACK измерять даже при более поздней ошибке.
Block timestamp — приблизительный возраст, не точное время доставки/включения.

Приёмка: deterministic tests порядка и вложенных tx, пропусков/ошибок/переполнения;
включение метрик не меняет решения и не требует синхронной записи диагностики.
Измерить overhead on/off; диапазон измерительной погрешности учитывать в выводах.

## 6. Воспроизводимый baseline и budget — P0.2

Расширить существующие инструменты. До оптимизации зафиксировать commit, сборку,
macOS/CPU, версии Python/web3, настройки, seed, block/hash, маршруты, размер
позиции, состояние allowance, режим warm/cold, RPC alias и профиль нагрузки.

Четыре разных набора, не выдавать один за другой:

1. Офлайн replay одинакового потока событий: стратегия, очередь, CPU, overhead.
2. Fork на фиксированном блоке с восстановлением snapshot между A/B: подготовка,
   approve, swap, receipt, сбои; gas и задержки fork не представляют mainnet.
3. Read-only RPC: V2/V3, block/head/log, quote на размер; public/paid, cold/warm.
   Чередовать A/B или использовать одинаковые временные окна и нагрузку;
   не перегружать public RPC. Кеш-hit без нового блока учитывать отдельно.
4. Видимый PAPER на свежих рынках: суммы $20, DIP 10%, TP/SL 15%, slippage 5%,
   Dynamic 120; продолжение после SL/cooldown явно фиксировать. Сохранять модель
   расходов, не обнулять её ради результата. Проверять базу WBNB/BNCB/другую,
   quote asset/USD и canonical pool; отсутствие WBNB-пула не означает отсутствие рынка.

Для RPC сравнивать время запроса, block lag, относительное время получения одного
и того же block hash/log, reconnect, 429, timeout. Не утверждать точное время
появления события в сети по часам клиента. Nonce benchmark — только read-only
выделенный публичный адрес, без ключа. Проверять переиспользование соединений;
DNS/connect/TLS выделять лишь при доступной надёжной instrumentation, не угадывать
их по общему времени eth_call. HTTP batch и Multicall сравнивать отдельно.

Минимум три повтора A/B. Для чтений накопить ≥1000 независимых наблюдений на cohort
в пределах лимитов; p99 при меньшем N помечать предварительным. Для устойчивой
оценки хвоста нужны дополнительные серии; не отправлять тысячи LIVE-транзакций
ради статистики. Искусственные повторения одного cached block независимыми не считать.

Целевой budget после baseline, до правок:

| Часть | Baseline | Цель | Условие |
| --- | --- | --- | --- |
| Доставка/получение цены | UNKNOWN | По измеренному RPC/WSS | Не ухудшить freshness/потери событий |
| Очередь + решение | UNKNOWN | Число ms по CPU-профилю | Прежний результат стратегии |
| Проверки + подготовка | UNKNOWN | Уменьшить измеренный критический путь | Все обязательные guards сохранены |
| Подпись | UNKNOWN | Оптимизировать только при заметной доле | Прежние tx fields/hash |
| Durable save | UNKNOWN | По storage benchmark | Та же crash durability |
| Отправка → ACK | UNKNOWN | Отдельно для каждого RPC | Unknown outcome не скрывается |
| Событие → swap ACK | UNKNOWN | Предварительно ≥15% снижения p95 | Три сопоставимых серии, выигрыш больше шума |

15% — критерий полезности, не обещанный результат. Если baseline показывает иной
потенциал, зафиксировать обоснованный budget до эксперимента. Не принимать выигрыш
при ухудшении SELL/STOP, свежести, частоты ошибок или нарушении инвариантов.

## 7. Оптимизации по измеренным причинам

### P0.3. RPC, ожидания, планировщик

- Инвентаризировать `sleep`, `Event.wait`, `Queue.get`, Qt timers, HTTP/WSS
  timeouts, receipt polling, SDK retry. Для каждого: файл/функция, назначение,
  длительность, interruptibility, stale budget, зависимость, решение keep/change.
- Проверить forced `Chain.check()` против кеша identity; общие снимки проверять
  по endpoint generation, chainId, block hash, max age. Не смешивать `latest`
  разных RPC как одно состояние. Не кешировать price как свежую после ошибки.
- Удалять только доказанные дубли в рамках одного валидного снимка. Проверить
  getCode/router metadata, повторные headers и дополнительные вызовы build_transaction.
- Объединять независимые contract reads Multicall на одном block/hash, учитывая
  ограничения calldata, частичные отказы и семантику msg.sender. Нельзя подменять
  симуляцию кошелька вызовом с sender Multicall.
- Измерить keep-alive/pooling и default timeout (сейчас Chain до 10 с по умолчанию).
  Разделить deadlines чтения/подготовки/receipt; таймаут не отменяет удалённую отправку.
- Ограниченный параллелизм read-only, без передачи mutable Chain между задачами:
  `checked_header`, caches и price snapshots сейчас изменяемые. Результаты публикует
  владелец исполнения только после проверки поколения и согласованности.
- Протестировать read failover и circuit breaker без лавины retries; все попытки
  входят в общий deadline. Отправку tx не помещать в универсальный retry wrapper.

Приёмка: меньше wire round trips/критический путь, одинаковые проверки; 429/503,
задержка, отставший/неверный RPC, STOP, смена токена и старый ответ не вызывают BUY.

### P0.4. Доставка WSS и локальная цена

Сначала сравнить существующие HeadFeed+HTTP и polling на одинаковых событиях.
Не менять на первом шаге Strategy.observe и семантику `max_gap=0.55`.

Если доказана польза: добавить shadow-поток logs для выбранного пула. Учитывать
blockHash/txIndex/logIndex, дубли, out-of-order, removed, reorg, reconnect/backfill,
смену подписки, initial HTTP snapshot и атомарный переход к live-потоку.
При пропуске — invalidate, resync и запрет входа до согласования.

V2 Sync может дать reserves; V3 Swap — spot-поля, но для полной локальной quote
нужны ticks/liquidity и изменения Mint/Burn. Не обещать заменить Quoter одним
Swap-event. Новые внутриблочные наблюдения способны менять DIP/TP/SL: shadow
сравнение обязательно; изменение частоты решений выделить как отдельную семантику.
Pending/mempool не является подтверждённым состоянием и не входит в обязательный
этап; не превращать его в новый сигнал стратегии. SSE не внедрять без источника.

Приёмка: локальные данные совпадают с canonical HTTP на проверяемом состоянии,
нет повторных сделок; пропуски не выданы за восстановленную полную историю.

### P1.1. Подготовка tx, nonce и gas

Матрица кеша обязательна: ключ, TTL/условие свежести, источник, инвалидирование,
последствия ошибки. ABI/selectors/metadata подготовить при выборе рынка;
amount/minOut/deadline/nonce/gas окончательно формировать по актуальным условиям.
Router/pool identity, proxy metadata, balance/allowance не считать вечными.

Nonce: сначала сравнить цену нынешних pending+latest checks с альтернативой.
Сохранить single writer per chain/wallet и durable reservation. На restart,
смене RPC, расхождении nonce, внешней tx, replacement/reorg или lost ACK —
reconcile, а не слепой increment/decrement. Ускоренная схема остаётся опциональной,
если безопасного выигрыша нет. Не вводить несколько pending swaps как «оптимизацию».

Gas: сначала измерить estimateGas и связь с реальными state/amount/allowance.
Не заменять его постоянным лимитом для произвольных мем-токенов. Предварительная
оценка — подсказка, требующая свежести/инвалидирования; экономию доказать на fork.
Текущая gas price приходит из конфигурации — не предполагать лишний eth_gasPrice,
пока wire trace его не показал. Approve после signal измерять отдельно; unlimited
approve или предварительная реальная отправка не являются частью этого плана.

Приёмка: stale balance/allowance, external nonce, revert, approve race, STOP между
sign/save/send, lost ACK, crash/restart. Ни один сценарий не создаёт второй swap
или повторную подпись после неопределённого результата.

### P1.2. Хранилище, фоновые задачи и UI

Профилировать JSON validation/serialization/fsync отдельно; использовать существующий
Ledger cache. Диагностика/архив/UI — ограниченные очереди, счётчики drops,
backpressure без блокировки executor; критические ошибки не терять молча.
Сигналы торговли нельзя просто отбрасывать как кадры графика.

Если Store.save действительно доминирует, отдельно спроектировать маленький durable
journal + snapshot с миграцией и fault-injection. Не заменять текущий протокол
асинхронным fire-and-forget. Отдельный writer допустим только с подтверждённым
durable ACK до broadcast и теми же гарантиями восстановления.

Приёмка: большой реалистичный журнал, disk full/fsync/replace faults, переполнение
метрик, медленный UI, завершение QThread, отсутствие вечных потоков. Не перестраивать
исполняемый `.app` во время измерения; прежний тест был загрязнён такой пересборкой.

### P2. CPU и P3. Уборка

Только после P0/P1 и профиля cProfile/py-spy: contracts/ABI reuse, преобразования,
объекты, JSON и Decimal. Высокочастотный profiler запускать отдельно от контрольного
latency-прогона. Не заменять финансовые int/Decimal на float. Полный asyncio или
multiprocessing вводить лишь при измеренной необходимости; текущая Qt/thread модель
сама по себе не дефект. Косметический рефакторинг вне критического пути отложить.

## 8. Правила failover и исполнения

Разделить read, broadcast и WSS endpoints. Резервный узел проверяет ту же сеть,
каноничность и достаточную свежесть. Быстрый ответ от отставшего узла не является
победой benchmark. Hedged reads допустимы только с ограничением нагрузки и явным
выбором согласованного результата; наличие нескольких провайдеров не гарантирует независимость.

Никакого автоматического send retry, fan-out в public mempool или нового nonce
после timeout. Возможную повторную отправку **тех же байтов** проектировать отдельно
после доказательства корректности; по умолчанию сохраняется текущая блокировка.
Не выдавать private RPC за MEV-защиту и не сливать транзакцию на public fallback.
SL и STOP не обходят unknown-transaction latch.

## 9. Финальная приёмка и формат результата

После каждого этапа: ограниченный diff → соответствующие регрессии → сопоставимый
benchmark → проверка результата → commit/push. Если ускорения нет, не объявлять
этап успехом по одному зелёному тесту; оставить измерения или откатить эксперимент.
Коммит не включает ключи, состояние кошелька, `.app` и сырые отчёты.

Финальные команды из корня (проверить актуальный AGENTS.md перед исполнением):

```bash
uv run --frozen ruff check dipbot tests tools launcher.py
uv run --frozen ruff format --check dipbot tests tools launcher.py
uv run --frozen mypy
uv run --frozen pytest -q
QT_QPA_PLATFORM=offscreen uv run --frozen python launcher.py --smoke-test
./BUILD_MAC.command
QT_QPA_PLATFORM=offscreen 'dist/DipBot Mac.app/Contents/MacOS/DipBot Mac' --smoke-test
codesign --verify --deep --strict 'dist/DipBot Mac.app'
```

Затем read-only benchmark и PAPER через уже собранное приложение: одинаковые
настройки, несколько актуальных токенов, естественные BUY/TP/SL и повторный вход,
отдельно trailing/STOP. 10–15 минут — техническая проверка, а не обязательное время
торговли одним умершим рынком. Фиксировать ручные вмешательства и смены рынка;
отсутствие естественного сигнала не заменять ручным BUY в отчёте об автоматике.
Не требовать суточного прогона: пользователь ранее исключил его из задачи.

Fresh migration timestamp брать из проверяемого события/источника; время создания
пары не всегда равно времени миграции. Для рынка записывать возраст, reserves,
исполняемые BUY/SELL quotes на $20, активность, источник USD, доступность выхода.
Нехватку исторических данных отмечать, не объяснять ею задним числом каждый SL.

Обязательные артефакты в `.local-artifacts/performance/<run-id>/`:

- manifest с точной командой без секретов, commit/settings/environment и cohort;
- before/after traces и сводки, errors/drops/число наблюдений;
- bottleneck-таблица: файл/функция, факт или гипотеза, ms/RPC count, решение,
  ожидаемый эффект до опыта, измеренный эффект после, риск;
- карта DAG, sleep/timeout inventory, cache invalidation matrix;
- report: mean/p50/p95/p99/max, RPC/последовательные round trips, freshness,
  успех/ошибки/reverts, UNKNOWN и непроверенные режимы;
- UI-снимки без секретов и сверка P&L/сделок/архива.

Сводку результатов обновить в `CURRENT_STATUS_RU.md`, команды — в `tools/README.md`.
Формула улучшения для сопоставимого percentile: `(before - after) / before × 100%`.
Не выводить число при нулевом/отсутствующем baseline и не смешивать разные cohorts.

Критерий завершения: измерительная инфраструктура и повторяемый benchmark готовы;
каждый найденный bottleneck исправлен с доказательством либо обоснованно оставлен;
безопасность и стратегия сохранены; тесты/сборка прошли; все ограничения перечислены.
Paid/mainnet результаты без соответствующего доступа/бюджета остаются UNKNOWN.

## 11. Выполнение: baseline и решения (27.09.2026)

P0.1 внедрён в `44342ad`; P0.2 сохраняется в
`.local-artifacts/performance/baseline/`. Данные локальных fork в отчётах отделяются
от LIVE, несмотря на использование настоящего LiveTrader. Полный набор: 882 теста;
сквозная проверка архива добавлена отдельно: новые поля проходят его allowlist.

Измерения до оптимизации (Intel Mac, Python 3.12; числа не являются production SLA):

| Участок | Baseline | Решение / предварительный budget |
| --- | --- | --- |
| Решение на 4 синтетических ценах | p50 ~0,015 мс; trace добавляет ~0,025 мс | Не менять Decimal/стратегию |
| Создание контракта + encode getReserves | p50 1,03–1,04 мс, p95 1,27–1,39 мс; 3×1000 | Кешировать только ABI factory; цель ≥20% уменьшения CPU на этом участке |
| Fork V2/V3 BUY/SELL | Три прогона каждого, один fixed block на router; 56–60 provider calls/цикл | Это локальные вызовы и upstream lazy reads, не mainnet latency. Не сокращать проверки ради числа |
| Store.save: 100/1000/10000 закрытий | warm median ~0,88 / 2,73 / 12,69 мс | Durable барьер сохранить; маленький отдельный journal пока не оправдан |
| Сводка расходов 10000 закрытий | ~38 мс | Вызывается отчётом вручную, не каждым тиком. Не приоритет hot path |

Cache budget фиксируется до изменения: ABI factory не содержит balance, allowance,
nonce, state или цены. Ключ — содержимое ABI; область — один Web3/Chain, ограниченный
LRU. Смена Web3 и изменение ABI должны исключать повторное использование. Кеш не
может менять calldata. Проверить исходный и кешированный путь в чередующихся сериях.

Инвентаризация ожиданий сохранена в `baseline/waits.json` (51 место, включая UI/checks).
Критические группы и решения:

- Worker: очередь до 50 мс, интервал учитывает длительность чтения; HeadSchedule
  ограничивает отложенное чтение 300 мс. Сначала shadow-сравнение, не менять cadence.
- Chain: timeout 10 с по умолчанию; MarketMonitor/GapRecovery 2 с. Это верхние границы,
  не искусственная пауза каждого успешного запроса. Сокращение требует измеренных
  хвостов, иначе создаёт ложные отказы. Не менять по единичному быстрому ответу.
- HeadFeed: connect/request 5 с, recv 250 мс, reconnect 0,5→10 с, close/join ограничены.
  Ожидания нужны для health/переподключения, не являются задержкой доставки готового recv.
- Exit reads: 0,5/1/2 с, STOP прерывает ожидание; receipt/accounting retry 2×0,2 с.
  Повторяется только чтение, send не повторяется. Сохранить антишторм/ambiguous latch.
- Receipt: 120 с / polling 0,2 с. Это наблюдение подтверждения, а не ACK; зависимый
  swap после approve должен дождаться receipt. Не заменять оптимистичным продолжением.
- PAPER: заданная задержка исполнения моделирует рынок; не удалять ради benchmark.
- Recorder: очередь неблокирующая, get 0,1 с / join 0,5 с; UI timer/debounce и shutdown
  не менять как «ускорение стратегии». Проверять drops/завершение отдельно.

P0/P1 решения: нынешние forced network checks перед send, pending+latest nonce,
estimateGas, allowance и canonical reads сохраняются. Их актуальность важнее
экономии неподтверждённого RPC. Новая параллельная работа с mutable Chain и локальный
nonce allocator не вводятся без сравнимого доказательства выигрыша и согласованности.

### P0: проверка identity пула через Multicall

До правки три независимых identity-чтения выполнялись последовательно. Они теперь
прикреплены к одному номеру блока, затем factory подтверждает canonical адрес на
том же блоке и повторно проверяется hash. Только эти неизменяемые поля канонических
Pancake пулов идут через Multicall; симуляция кошелька, баланс/allowance и send — нет.
Частичный результат/ошибка декодирования/reorg запрещают продолжение.

Read-only A/B: 3 серии × 5 пар каждого V2/V3, чередование порядка, одинаковые
добавленные canonical guards. V2 медианы direct 831–863 мс → batch 681–702 мс;
V3 906–936 → 765–821 мс. Wire calls warm: 11→9 и 12→10. Ошибок/расхождений пула 0.
По отношению к прежнему коду экономится **один**, а не два запроса: добавлена
сверка hash snapshot. Малый N не подтверждает p99 или выигрыш полного BUY→ACK.
Команда воспроизведения: `uv run --frozen python -m tools.rpc_latency_probe --identity
--samples 5 --output .local-artifacts/performance/identity-ab.json` (одна строка).

Baseline public RPC импортировал код до первого performance-коммита; поле commit
старого отчёта ошибочно брало HEAD в конце измерения. Это учтено при сравнении:
`baseline/rpc.json` не считать запуском кода его конечного HEAD. Новые отчёты
фиксируют commit и SHA256 исходников **до** запуска. Сырые результаты сохранены.

### Контроль fork и пределы вывода об ускорении

Последовательные серии на разных Anvil-процессах не подтвердили ускорение всего
цикла: upstream lazy reads и дополнительный receipt poll давали скачки 200–400 мс,
включая ухудшение отдельных SELL. Эти результаты сохранены, а не отброшены.
Добавлен `fork_roundtrip --paired-performance`: один процесс, snapshot между A/B,
одинаковые суммы/allowance, отдельное локальное управление майнингом перед чтением
receipt. Внешний proxy по-прежнему допускает только read-only методы.

Парный V2 без управления майнингом: median BUY ~375→362 мс, SELL ~365→351 мс,
N=3 на вариант; V3 остаётся чувствителен к receipt polling. В режиме управляемого
майнинга V2 BUY ~723→705 мс, SELL ~528→531 мс — **ускорение полного SELL не доказано**.
Это разные fork cohorts, не mainnet before/after. Изменения приняты по проверенному
сокращению сетевых round trips проверки identity, эквивалентным финансовым результатам
и сохранённым guards; процент ускорения event→broadcast BSC остаётся UNKNOWN.

P1/P2: переписывание executor на asyncio, локальное распределение nonce, отказ от
estimateGas, замена подписи/Decimal и новый журнал не внедрялись. Профиль не дал
оснований рисковать ими: CPU решения ~0,015 мс, основная задержка — необходимые
RPC и подтверждение approve. Сводка расходов вручную не включена в hot-path бюджет.
Дополнительный pool-log engine отложен: существующий HeadFeed уже доступен; другой
набор внутриблочных наблюдений меняет стратегию и требует отдельной shadow-валидации.
