# Расширенный статический проход: unwind, конвертер и реестр

2026-09-24. Оригинал не запускался. Production-код Mac в этом проходе не менялся. **Весь список реверса не закрыт**: ниже отделены новые доказательства от оставшихся задач.

## Охват и воспроизводимость

[UNWIND_INVENTORY_EVIDENCE.json](UNWIND_INVENTORY_EVIDENCE.json) охватывает все **231 тело** из существующих двух карт фабрик: 198 методов и 33 функции runtime_config/secure_store. Суммарно по телам пройдено 247 260 инструкций, записано 5064 обращения к известным помощникам, учтён 301 диапазон unwind. Это не число всех функций EXE и не число доказанных динамических вызовов.

`tools/unwind_inventory.py` проверяет SHA-256 EXE и входных карт, следует прямым переходам, разрешает цепочки UNW_FLAG_CHAININFO и сохраняет публичные имена/скалярные аргументы. Косвенные переходы и вызываемые функции автоматически не исполняются. Пределы: 30 000 инструкций на тело, прямые переходы в пределах 64 KiB от входа. Шесть достижимых trap-границ остались явно незамкнутыми; продолжения после INT3 не выдумываются. JSON `null` в аргументах означает неизвестное значение, а не доказанный Python None; None внутри восстановленного literal tuple имеет другое значение.

В окружении с Capstone/pefile:

```bash
python -m tools.unwind_inventory /path/to/reference.exe --output docs/UNWIND_INVENTORY_EVIDENCE.json
python -m tools.floss_receiver_requirements docs --inventory docs/UNWIND_INVENTORY_EVIDENCE.json --output docs/FLOSS_EXPANDED_REQUIREMENTS.json
python -m tools.post_send_audit /path/to/reference.exe --output docs/POST_SEND_EVIDENCE.json
python -m unittest discover -s tools/tests -q
```

## Нативные исключения и REMOVE

Для 73 из 301 диапазона, включая разрешённые цепочки, указан один обработчик: `0x14292c66c`. У остальных 228 обработчик в рассмотренных unwind-цепочках отсутствует. Это **не** отсутствие Python try/except.

Проверена реализация обработчика: он вызывает `0x14292c68c`, восстанавливает cookie стека, передаёт её в checker `0x14292b7d0` и при нормальном возврате возвращает 1. Checker сравнивает cookie с глобальным значением; несовпадение уходит в другую ветвь. Здесь не обнаружен обработчик восстановления `_records`, записи файла или повторной отправки транзакции. Байтовые хеши — в [POST_SEND_EVIDENCE.json](POST_SEND_EVIDENCE.json).

Это снимает неопределённость о назначении **данного** SEH-обработчика. Не закрывает косвенные Python-вызовы, дескрипторы, деструкторы и возможные изменения binding. Для REMOVE по-прежнему доказан `pop → _save → выход из lock`, но полный rollback памяти через все вызываемые объекты не доказан.

В карте есть 48 методов Trader, определения `Trader.close` среди них нет. Это ограничение карты, а не доказательство отсутствия runtime-атрибута. `_close_trader` остаётся условным getattr/callable-вызовом.

## V3: фактический остаток между swap и unwrap

В `Trader.execute_quote_to_bnb`:

1. До swap читается WBNB balance: вызов `0x141e7fed8`, результат сохраняется в R13.
2. После send/wait/status снова читается WBNB: `0x141e806a2`.
3. `0x141e806d9` вычисляет `after - before` через ранее разобранный helper вычитания.
4. `0x141e80700` загружает общий ноль из `0x1429a02b0`; `0x141e8070e` сравнивает прирост с нулём через helper `<=`.
5. При `delta <= 0` выполняется ветвь ошибки, положительный прирост ведёт к последующему withdraw.

Этот локальный порог не является доказательством отсутствия других защит маршрута или router minOut. Mac дополнительно проверяет `received >= minimum` после receipt и сохраняет эту более строгую проверку.

`tests/test_converter_stage_faults.py`: 10 сценариев с настоящим журналом на временной файловой системе, локальной подписью одноразовым пустым ключом и подменённым транспортом. Границы прироста `-1/0/1/195/196/200` при minOut=196; ошибка чтения баланса после swap; ошибка оценки газа unwrap; потеря ответа send и receipt unwrap. Проверяются отдельные записи confirmed swap / pending unwrap, отсутствие повторного begin после перезапуска и вывод только нового WBNB без исходных 1000 raw units. Полноценные RPC, процесс Windows и реальные транзакции не используются.

## Загрузка профилей и fallback

В `DynamicPairRegistry._load` проверена отдельная ветвь:

- `0x140bb887b` сопоставляет исключение с Exception;
- `0x140bb889b` вызывает конструктор пустого dict `0x1428fec80`;
- `0x140bb8931` присваивает этот dict в `_records`;
- `0x140bb8974` получает `__name__` типа исключения, `0x140bb89a7` записывает его в `load_error`.

Конструктор использует PyDict_Type / freelist, устанавливает число элементов в ноль. Очистка найдена в **_load**, не в _save: её нельзя объявлять rollback после REMOVE. Ошибки самого обработчика тоже возможны. Новая версия защищённого формата или миграция этим не обнаружена.

Mac не заменяет повреждённый реестр пустым при чтении каталога, ADD или REMOVE. Три дополнительных сценария в `test_catalog_commit_boundaries.py` подтверждают отказ для неизвестной версии и сохранение исходной памяти/файла. Это намеренное отличие, а не тест исполнения Windows.

## Что действительно осталось

Полные условия всех вложенных маршрутов/ошибок Sweep; rollback через косвенные вызовы; реализация динамического close и завершение задач; binding объектов и оставшиеся аргументы; рабочая модель Python/Nuitka для FLOSS; полнота событий AutoPair; остальные ветви изменения профилей и fallback защищённых настроек. Инвентаризация уменьшает область ручного поиска, но не закрывает эти семантические задачи автоматически.

Фактическое поведение Windows при авариях и сетевых сбоях, системный DPAPI и полное совпадение не подтверждаются этим Mac-only проходом.
