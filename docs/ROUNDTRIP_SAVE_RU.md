# Round-trip: целые bps и ошибка GUI REMOVE

2026-09-24. Продолжение [единого аудита](COMPREHENSIVE_AUDIT_RU.md). Windows-приложение не запускалось, RPC и системный DPAPI не использовались.

## Подтверждена операция округления потери

В native-функции `0x141e75b60–0x141e76003` оба входа проходят PyNumber_Long; обратный выход ограничивается снизу нулём. Для integer raw units прослежены:

- amount_in <= 0 → 10000 bps;
- reverse_out >= amount_in → 0 bps;
- иначе `(amount_in - reverse_out) * 10000 // amount_in`.

В цепочке арифметики `0x1429195a0` выбирает nb_subtract по смещению 0x08, `0x1429178d0` — nb_multiply по 0x10, `0x142916a40` — nb_floor_divide по 0xe8. Смещения сверены с локальным заголовком CPython 3.12 `cpython/object.h`; в x64 таблице это указатели по 8 байт. Множитель trader[131] декодирован как 10000. Итоговый PyNumber_Long не заменяет floor на деление через float.

`tools.native_models.roundtrip_loss_bps` моделирует только целочисленные входы. Произвольные объекты с переопределённым __int__ и глобальными binding не объявляются эквивалентными.

## Сравнение с реальным выбором маршрута Mac

Добавлены тесты `tests/test_roundtrip_boundary_comparison.py`: восстановленная арифметическая модель сравнивается с `LiveTrader.conversion_route`, transport заменён искусственными котировками.

| Вход | Обратный выход | Native loss bps | Windows-правило ≤1500 | Mac точные ≤15% |
|---:|---:|---:|---|---|
| 10000 | 8500 | 1500 | Допускает | Допускает |
| 1000001 | 850000 | 1500 | Допускает | Отклоняет |
| 1000000 | 849901 | 1500 | Допускает | Отклоняет |
| 1000000 | 849900 | 1501 | Отклоняет | Отклоняет |

Также проверены вход 10^30, точная граница и отклонение на одну raw unit: Mac не теряет это различие через float. Отдельные тесты проверяют native sentinel для нулевого/отрицательного входа и clamping отрицательного обратного выхода. Они не означают, что такие суммы допустимы для LIVE.

Дополнительная строгость Mac сохранена. Сценарий сравнивает статическую модель оригинала с Mac, а не два работающих бота.

## Аргументы сохранения и GUI-ошибка

Для `_save` по `0x140bb9ace` прослежены три аргумента: `self.path`, построенный документ и глобальный REGISTRY_PURPOSE. Автоматический анализ достоверно сохраняет третий аргумент; первый прослежен вручную через getter path, содержимое документа пока не восстановлено полностью. В отчёте это разделено, неизвестные значения не подменяются предположениями.

Добавлен помощник call_vector2 (`0x142907260`): проверены arity=2 и загрузки двух элементов из R8. Его синтетический тест проверяет порядок аргументов и сохранение неизвестного второго значения.

После нулевого возврата `registry.remove` GUI переходит через `0x14090842d` в `0x1409079d3`. От этой точки пройдены 202 инструкции. Обычные участки `_refresh_pair_selector_catalog` по `0x1409088ea` и `_schedule_autopair` по `0x140908d9a` недостижимы по прямым переходам этой ветви. Вызовы и SEH здесь не раскрываются; нельзя утверждать, что никакой вызываемый код не обновляет UI. Возврат записи в `_records` всё ещё не доказан.
