# Nonce, повторный ответ RPC и receipt

2026-09-24. Продолжение [разбора Sweep](SWEEP_INTERNALS_RU.md). Оригинал не запускался. Ни одна проверка не обращалась к реальному RPC, пользовательскому ключу или состоянию. Статические выводы проверены по машинным инструкциям и r2ghidra-псевдокоду.

## Оригинальный Trader

| Метод | Подтверждённое поведение |
|---|---|
| `_next_nonce`, 0x141e65a10–0x141e6629b | Под `_nonce_lock` читает текущий счётчик, увеличивает его на 1, возвращает прежнее значение |
| `_sync_nonce_from_network`, 0x141e662a0–0x141e66c05 | Под той же блокировкой записывает get_transaction_count(address, 'pending') в `_nonce` |
| `tx_base`, 0x141e66c10–0x141e670ef | Получает nonce через `_next_nonce` при подготовке полей транзакции |
| `send`, 0x141e670f0–0x141e67cfb | Подписывает, получает локальный hash, вызывает send_raw_transaction. При Exception синхронизирует nonce, проверяет lowercase текста на `already known` / `known transaction`; в этих случаях возвращает локальный hash, иначе распространяет ошибку |
| `wait`, 0x141e67d00–0x141e68294 | Вызывает wait_for_transaction_receipt с переданным timeout (по умолчанию 120 с), poll_latency=0.2. Синхронизирует nonce при успешном возврате и в ветке исключения |
| `WalletSweepEngine._close_trader`, 0x142093c20–0x142093f94 | Получает необязательный close, проверяет callable и вызывает его. Сам метод не записывает журнал и не сверяет receipt |

Ключевые точки: sync при send-ошибке `0x141e6779e`; две проверки строк `0x141e67879` / `0x141e678b4`; wait poll interval `0x141e67e0f`; sync на выходах wait `0x141e67f9a` / `0x141e68045`.

Синхронизация pending nonce не означает подтверждение транзакции: одинаковый счётчик может наблюдаться при разных состояниях mempool. В этих методах не найдено записи hash/receipt в durable-хранилище. Это ограниченный вывод по указанным телам, не доказательство отсутствия другого журнала во всём приложении.

[NONCE_EVIDENCE.json](NONCE_EVIDENCE.json) содержит выбранные публичные константы и SHA256 шести диапазонов:

```bash
uv run --frozen python -m tools.nonce_native /path/to/original.exe --output /tmp/nonce.json
```

## Изменения Mac

Ветка `already known` / `known transaction` теперь продолжает ожидание **по локальному hash**, который уже записан до отправки. Второй broadcast, новая подпись и новый nonce не создаются. Сообщение RPC само по себе ничего не подтверждает: требуется receipt. При таймауте остаётся pending и блокировка. Остальные ошибки отправки, включая nonce too low, сохраняют прежнее поведение: требуется сверка.

Дополнительно ужесточена проверка receipt при обычном ожидании и ручной сверке. Обязательны совпадающий 32-байтный transactionHash, целочисленный status 0/1 и неотрицательный целочисленный blockNumber. Чужой hash, неполные или повреждённые поля не меняют запись на confirmed/reverted. Сверка проверяет chain через Chain.check. Это собственное усиление Mac; наличие таких проверок в Windows не утверждается.

Mac не перенимает оптимистическое увеличение локального nonce: перед каждой отправкой читает pending/latest и отклоняет внешнюю pending-транзакцию. После потенциальной отправки durable-журнал остаётся обязательным. Сверка завершённых receipts не снимает блокировку автоматически; пользователь отдельно сверяет реальные остатки.

Проверка receipt не доказывает финальность или отсутствие reorg и не защищает от RPC, подделывающего полностью согласованный ответ. Проверка canonical blockHash/подтверждений в этот проход не добавлялась.

## Что осталось неизвестным

- Полный жизненный цикл Windows Trader, других хранилищ и возможных обработчиков crash/restart вне разобранных методов.
- Эффект close конкретного trader/provider и поведения Web3 оригинала при сетевых обрывах.
- Сравнительные Windows/Mac трассы, reorg/finality, пропавшие/заменённые транзакции и LIVE-исполнение.
- Защищённая миграция DPAPI и периодический polling PENDING: статус прежний, не подтверждено.

Ограничение «без запуска оригинала» сохранено. Новые выводы сужают неизвестную область; полная runtime parity не объявляется.

## Проверки

Новые offline-сценарии: оба текста known-transaction в разном регистре, receipt success/timeout без повторной отправки, неподходящий hash/status/blockNumber при send и reconcile, bytes/HexBytes hash, повреждённый receipt, отказ nonce too low без повторной отправки. Дочерние crash-тесты продолжают использовать подставной receipt с локальным hash.

Итоговый результат тестов и macOS-сборки: [VALIDATION_RU.md](VALIDATION_RU.md).
