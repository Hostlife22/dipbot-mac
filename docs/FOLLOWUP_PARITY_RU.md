## REMOVE: уточнённая последовательность

В `CommercialGUI.remove_current_live_pair` (`0x140907240–0x1409093a9`) видны:

1. Проверка динамического профиля; отказ для встроенного.
2. Проверки `_live_pair_busy`, `_wallet_sweep_running`, `_manual_lock.locked`, работающего bot и `_position_open`.
3. Диалог подтверждения с предупреждением сначала продать target/base.
4. Переключение на доступный DEFAULT_PAIR под `_autopair_applying`.
5. `registry.remove`, `install_dynamic_pair_profiles`, пересчёт адресов баз, обновление selector и состояния удаления.
6. Сообщение о результате, `_schedule_autopair(token.text())` (`0x140908d9a`), `QTimer.singleShot(0, _request_pair_holdings_refresh)` (`0x140908ed3–0x140908f1f`).

В этом теле **нет прямого чтения on-chain балансов**. Текст диалога не является доказательством проверки остатков; наличие ограничений внутри registry.remove ещё требует отдельного разбора. Mac сохраняет более строгую проверку фактических остатков и сохранённых позиций.

Перенесён повторный AutoPair после успешного удаления. Обновление каталога сохраняется до события повторного поиска; неудачное удаление не запускает его. Дополнительно REMOVE заблокирован при незавершённой Mac-операции, даже если текущая позиция уже очищена. Автоматическое обновление holdings оригинала и его UI-диалог целиком пока не перенесены.

## Sweep: подтверждённое отличие обработки ошибок

`WalletSweepEngine.run` вызывает `_sell_target` (`0x14209b816`), формирует TARGET FAILED и `; continuing` (`0x14209c2c4`); аналогичная ветка есть для BASE (`0x14209d921`). Финальная проверка отдельно учитывает недоступные балансы (`wallet_sweep[211]`), затем присутствует `_sync_nonce_from_network` (`0x14209edfa`). Это уточняет прежнее UNKNOWN: продолжение при ошибках есть в оригинале, но характер ошибки и состояние отправки определяются также внутренними методами.

Mac продолжает после ошибок предварительного чтения/выбора маршрута. После durable begin исключение останавливает Sweep и сохраняет журнал для сверки. Перенос общего catch-and-continue после потенциальной отправки без разбора `_sell_target`, `_convert_base` и их журналирования мог бы разрешить повторную отправку. Поэтому это остаётся **явным отличием**, а не MATCH. Синхронизация nonce оригинала сама по себе не доказывает восстановление receipt/позиции.

Следующий статический шаг: тела `_sell_target`, `_convert_base`, влияние исключений на nonce и tx_hashes; проверка фильтра пыли и сценариев частичного исполнения. Windows runtime по этим ветвям не проверен.

## Защищённый формат

Уточнён контракт `write_protected_json` / `read_protected_json`:

- Версия 1: присваивание VAULT_VERSION из глобальной константы int 1 в `0x141dd2251–0x141dd2264`.
- Внутренний JSON: ensure_ascii=True, sort_keys=True, separators=(',', ':'); UTF-8 bytes передаются protect_bytes вместе с purpose.
- Внешний JSON: format `NRNF-DPAPI`, version, base64 payload, сортировка ключей и компактные разделители, ASCII.
- Чтение: проверка format; `int(version)`; `b64decode(validate=True)` в `0x141dce77e`; unprotect; UTF-8 JSON; проверка dict в `0x141dceab5–0x141dceac3`.
- Ошибка превращается в общее сообщение о повреждённых/недоступных локальных данных.

`tools/protected_format.py` воспроизводит только сериализацию и проверки. Protect/unprotect явно передаются вызывающим кодом. В нём нет portable-шифрования, обхода DPAPI, чтения файлов, работы с лицензией или подключения к Mac Store. Тесты используют синтетические bytes. Это **не готовая миграция защищённого Windows-хранилища**: криптографическая совместимость, purpose/entropy каждого файла и разрешённый экспорт на исходной Windows ещё не проверены.

## PENDING: расширена проверка ссылок

Просканированы RIP-relative MOV/LEA ссылки на `_autopair_timer`, `_schedule_autopair`, STATUS_PENDING. Дополнительные обращения к таймеру в `0x140922010–0x140922552` относятся к closeEvent и stop, а не к периодическому запуску. Ссылка STATUS_PENDING в `0x14091b630–0x14091c89d` находится в проверке состояния перед действием и не перезапускает таймер. После ADD/REMOVE есть явный повторный поиск.

В проверенных местах периодический polling PENDING не найден. Такой scan не покрывает произвольную косвенную диспетчеризацию и не является математическим доказательством отсутствия другого таймера. Не добавляем предполагаемое поведение в Mac под видом восстановленного. Остаётся debounce 220 мс и повторный поиск по действиям пользователя/после REMOVE.

## Runtime-сравнение

Не выполнено: сохранено ограничение не запускать оригинал. Для проверки нужны сопоставимые Windows/Mac трассы на одинаковых публичных ответах RPC либо фиксированном блоке, без публикации ключей, RPC credentials и подписанных транзакций.

| Сценарий | Что сравнить |
|---|---|
| PENDING → появление ликвидности без ввода | Появится ли новый RPC сам; источник события и задержка |
| REMOVE встроенного/занятого/отсутствующего профиля | Отказ, изменение selector/каталога, запуск AutoPair/holdings |
| TARGET balance timeout / нет маршрута | failed/skipped, продолжение со следующим target |
| Ошибка до отправки / receipt timeout после отправки | nonce, tx_hashes, повтор/остановка, состояние после перезапуска |
| Остаток TARGET/BASE / ошибка финального чтения | remaining/unknown и итоговый статус |
| Повреждённый envelope / версия / неверный purpose | Класс отказа, сохранение старых данных, отсутствие автоматической перезаписи |

Подставные callbacks/тесты не заменяют эти трассы. Windows crash/restart и LIVE parity остаются UNKNOWN.
