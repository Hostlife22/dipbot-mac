# Ошибки после отправки и продолжение Sweep

2026-09-24. Продолжение [аудита shutdown](SHUTDOWN_AUDIT_RU.md). Оригинал не запускался; production-код Mac не менялся.

## Что подтверждено в оригинале

Успешный путь `_sell_target` проходит ожидание receipt и проверку status, затем вызывает `_close_trader` по `0x1420982c2`. Нулевой результат закрытия ведёт к ошибке через `0x142098610`, а не к обычному возврату результата продажи.

При уже возникшем исключении `_close_trader` вызывается по `0x142098581`. Если закрытие тоже завершается ошибкой, код берёт текущее исключение из tstate и идёт в очистку. Если закрытие прошло, используется обычный путь повторного возбуждения ошибки через помощник `0x142902000`. Это различие первичной ошибки и ошибки очистки; полное содержание цепочки исключений на runtime не проверено.

В `WalletSweepEngine.run`:

- после неуспешного `_sell_target` начинается обработка ошибки;
- `0x14209c00d` проверяет принадлежность к Exception;
- `0x14209c088` получает failed, далее выполняется append;
- формируется `TARGET FAILED ...; continuing`;
- нормальное завершение обработчика достигает чтения следующего элемента по `0x14209c407` и перехода `0x14209c412` обратно в цикл.

Ошибки самого обработчика могут выйти наружу. Это подтверждение возможности продолжения после ошибки, а не гарантия, что любой Exception всегда будет обработан успешно. Вложенный вызов мог уже отправить или подтвердить транзакцию: failed не означает «ничего не произошло».

## Наружный worker и UI

`_wallet_sweep_worker` формирует wallet_sweep_complete из результата run либо wallet_sweep_error через safe_error. В путях очистки присутствует `_manual_lock.release`. `_handle_wallet_sweep_error` вызывает `_finish_wallet_sweep_ui` и пишет `WALLET SWEEP ERROR` в журнал.

Снятие UI/manual lock не доказывает сверку баланса, отмену транзакции или восстановление durable-состояния. Эквивалент журнала Mac этим кодом не установлен.

## Проверки Mac после receipt

Добавлено пять сценариев `tests/test_receipt_storage_faults.py`. Используются реальный временный файл, настоящие вызовы os.fsync с искусственным отказом, эфемерная неподкреплённая подпись и полностью подменённый RPC.

1. Успешный/reverted receipt × ошибка fsync временного файла: на диске остаётся pending, повторная операция блокируется.
2. Успешный/reverted receipt × ошибка fsync каталога после replace: новый confirmed/reverted уже виден, но незавершённая операция сохраняется и блокирует повтор.
3. Ошибка callback уведомления после сохранения confirmed: отправленная транзакция остаётся записанной, новая операция запрещена.

В первых четырёх сценариях проверены текущий процесс, повторное чтение Store, reconcile и отсутствие второй отправки. Reconcile не снимает необходимость проверки баланса. Это инварианты Mac, а не тест исполнения Windows.

## Свидетельства и ограничения

[Хеши native-диапазонов и публичные имена](POST_SEND_EVIDENCE.json). Диапазоны являются адресными свидетельствами; инструмент не строит полный граф SEH/callee. Для методов worker/UI границы сверены с PE unwind. Подписи в тестах никуда не передавались за пределы подменённого transport.

```sh
python -m tools.post_send_audit "$EXE" --output docs/POST_SEND_EVIDENCE.json

```
